Overview

Campus Store Payments is a small online store with its own payments platform. Customers browse products, fill a cart and pay by card. The merchant gets a dashboard with revenue, success rate and decline reasons, can search every transaction, refund all or part of a payment, and watch signed webhooks being delivered to their server.

It is built around the problems that make real payment systems hard: retries must never charge twice, two people acting at once must not break the numbers, card data must not be stored, and the merchant must be told reliably about every change.

Data model

erDiagram USERS ||--o{ ORDERS : places ORDERS ||--|{ ORDER_ITEMS : contains ORDERS ||--o{ PAYMENTS : "paid by" CARD_TOKENS ||--o{ PAYMENTS : uses PAYMENTS ||--o{ PAYMENT_EVENTS : timeline PAYMENTS ||--o{ REFUNDS : has PAYMENTS ||--o{ WEBHOOK_DELIVERIES : notifies USERS ||--o{ IDEMPOTENCY_KEYS : sends
  • Money is an integer number of paise everywhere; never a float.
  • Public ids are random (pay_…, ord_…), so nobody can guess other customers' records.
  • card_tokens holds a token, brand, last 4, expiry and a keyed fingerprint (HMAC-SHA256 of the number with a server secret). Never the number, never the CVC.
  • A CHECK constraint keeps amount_refunded ≤ amount even if the code had a bug.

Never charging twice

sequenceDiagram participant C as Checkout participant API as FastAPI participant DB as Postgres C->>API: POST /payments, Idempotency-Key K API->>DB: INSERT key K, lock order, authorise, save, COMMIT API--xC: response lost (card WAS charged) C->>API: retry: same body, same key K API->>DB: key K exists, same body API-->>C: saved result, Idempotent-Replayed: true
  1. Insert the key first (INSERT … ON CONFLICT DO NOTHING). If another request with the same key is still running, Postgres makes this insert wait until it finishes.
  2. New key → run the action inside a savepoint, store its response on the key row, and commit once: action, key, audit row and webhook outbox together.
  3. Known key → same body: replay the stored response. Different body: 409, because a client bug must not receive someone else's result.
  4. An unexpected crash rolls everything back, key included, so the client can simply retry.

The browser creates one key per payment attempt and reuses it (and the same card token) for automatic retries; a new key is used only for a genuinely new attempt. The demo tool X-Simulate-Lost-Response commits the payment and then answers 503, to show the retry being replayed.

Card data and the fraud rule

The checkout sends the card to POST /api/cards/tokens, which plays the gateway's role: Luhn checksum, brand by IIN range, length, expiry (valid to the end of the month) and CVC length are checked, then the number and CVC are dropped. Only the token is used to pay. A test dumps every table after a payment and searches for the card number.

Velocity rule: if the same card (same fingerprint) was declined 3 times in the last 10 minutes, the next attempt is blocked without asking the issuer, recorded with the code velocity_blocked, shown on the dashboard and in the payment timeline. Both numbers are settings.

Refunds

  • Full (leave the amount empty) or partial; the status becomes partly refunded or refunded, and a full refund marks the order refunded.
  • Each refund form submission carries its own idempotency key, so a retried click refunds once.
  • Only succeeded or partly refunded payments can be refunded; more than what is left is a 409.
  • Every refund adds a timeline event, an audit row and a refund.created webhook.

Webhooks

  • Outbox: the delivery row is written in the same transaction as the payment, so an event is never lost or sent for a change that was rolled back.
  • Signature: Campus-Signature: t=<unix time>,v1=<HMAC-SHA256(secret, "t.body")>. The receiver recomputes it, compares in constant time and rejects timestamps older than 5 minutes (replays).
  • Retries: after 30 s, 1, 2, 4 and 8 minutes; then failed, with a manual retry button. Every retry has the same event id so the merchant can ignore duplicates.
  • In demo setups a built-in receiver verifies the signatures, so the log shows real signed deliveries end to end.

Accessibility and the frontend

  • Labelled fields with the right autocomplete tokens, errors linked by aria-describedby, an error summary that takes focus, a polite live region for payment progress, keyboard-only flow, a skip link.
  • Charts are SVG with text alternatives; status is never shown by colour alone.
  • Light theme with AA-contrast status pills; tables drop secondary columns on phones, so no page scrolls sideways at 375 px.
  • Demo mode: with no API URL configured, the same pages run against an in-browser stand-in (the GitHub Pages demo), with a banner saying so.

Backend tests run on a real PostgreSQL (CI uses a Postgres service container; locally a throwaway server is started), because row locks and ON CONFLICT behave differently in SQLite. GitHub Actions runs both suites and builds the API image; a second workflow publishes the demo-mode frontend to GitHub Pages. docker compose up runs Postgres, the API and the web app behind nginx; render.yaml deploys the same to Render.

Limitations

  • The gateway is simulated. A real store would use a provider's hosted card fields, so the card number never reaches this server (smaller PCI DSS scope).
  • The session token lives in localStorage; an httpOnly cookie with CSRF protection would be safer.
  • Metrics are in-process; one fixed fraud rule, not a model; dashboard history is simulated.

Interview questions

Why store the idempotency key in the same transaction as the payment?
If they were separate, a crash between them would leave a charge without a key (the retry charges again) or a key without a charge (the retry is wrongly told it worked).
What happens when two requests insert the same key at once?
The second insert waits on the unique index until the first commits, then finds the row and replays its stored response.
Why lock the payment row for refunds if there is a CHECK constraint?
The lock makes the second refund see the first and get a clear 409; the constraint is a last line of defence that would otherwise surface as a 500.
Why an outbox instead of sending the webhook in the request?
Sending inside the request could notify the merchant about a change that then rolls back, or lose the event if the process dies after commit. The outbox row commits with the change.
Why include a timestamp in the webhook signature?
Without it, anyone who captured one request could replay it forever; with it, the receiver rejects old requests.
Why a keyed fingerprint and not a plain hash of the card number?
Card numbers have little entropy; a plain hash can be reversed by hashing all candidates. The HMAC needs the server secret.
