Overview

Secure Checkout is a card payment page in React + TypeScript built around three promises to the customer: you are never charged twice, everyone can use it (keyboard and screen-reader users included), and help is there when a payment fails, from an assistant that answers from the help centre and cites its sources.

Never charging twice

sequenceDiagram participant U as Customer participant H as useCheckout participant G as Gateway U->>H: Pay (double-click) Note over H: 2nd click ignored (ref guard) H->>G: charge(card, key K) G-->>H: response lost (card WAS charged) H->>G: retry charge(card, same key K) G-->>H: original result, no new charge H-->>U: Payment successful •••• 4242
  • One key per attempt. The key is created when an attempt starts and reused for every retry of that attempt.
  • A new key only for a genuinely new attempt: after a decline, or when the card details change.
  • Same key, different payment → refused (IdempotencyConflict), so a bug cannot reuse a key by accident.
  • The double-click guard is a ref, not state: a state update would only take effect on the next render, after the second click.
  • Automatic retries (2, with back-off) after network errors; if they run out, the customer is told that pressing Pay again is safe.

Luhn checksum: from the right, double every second digit (subtract 9 if it exceeds 9) and sum everything; a valid number sums to a multiple of 10. It catches every single-digit typo and most swaps of neighbouring digits. Expiry: a card is valid until the end of its expiry month. Amounts are integers in paise, never floating point.

Accessibility

  • Every input has a visible label and the right autocomplete token (cc-number, cc-exp, cc-csc, cc-name) and a numeric keyboard on phones.
  • Errors appear after the user leaves a field (not while typing), are linked with aria-describedby and set aria-invalid.
  • On a failed submit, focus moves to an error summary whose items link to the fields.
  • Progress and results are announced through a polite live region.
  • The 3-D Secure dialog takes focus and closes on Escape; touch targets are at least 44 px; contrast ratios are chosen for WCAG AA.
  • axe-core runs in the tests on the empty form, the form with errors and the full page: 0 violations.

Payment help assistant (RAG)

A retrieval-augmented assistant over 10 help articles (21 sections) for payment questions.

  1. Retrieve: BM25 over title, heading and text, with synonym expansion (customers write "OTP", the articles say "code") and light stemming.
  2. Use context: the decline code of the last payment is added to the question, so "why did it fail?" is answered for this payment.
  3. Refuse when unsure: if the best section scores below 2.25 (chosen on dev questions only), it says it could not find the answer.
  4. Answer with sources: sentences quoted from the best sections, with the article and section shown. An optional LLM mode must cite the sources it was given, otherwise the quoted answer is used; the model is called through a backend, never with a key in the browser.

Limitations and next steps

  • The gateway runs in the browser. A real deployment moves it server-side and uses a payment provider's hosted fields, so card data never touches the app (PCI DSS scope).
  • The assistant's articles are written for this demo; real help-centre content and real customer questions would give a fairer evaluation.
  • Pretrained embeddings would help retrieval with vaguer questions.

Interview questions

Why must a retry reuse the same idempotency key?
If the first request charged the card but the response was lost, a new key would create a second charge. The same key makes the gateway return the original result.
Why is the double-click guard a ref?
State updates apply on the next render; two clicks in the same frame would both see "not busy". A ref changes immediately.
What does aria-live do here?
Screen readers announce status changes ("Processing…", "Your card was declined") without the user moving focus.
Why does the assistant refuse some questions?
A confident wrong answer about money is worse than "I could not find this; contact support". The threshold is chosen on dev questions, not test, to avoid overfitting.
What does Luhn not catch?
A valid-looking but non-existent card, and some digit swaps (09 ↔ 90). Only the issuer can confirm a card.
